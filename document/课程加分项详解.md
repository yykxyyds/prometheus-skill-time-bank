## 1. 安全认证 JWT

### 是什么？

JWT（JSON Web Token）是一种无状态的用户身份认证方式。用户登录后，服务端发一个"令牌"（token），之后每次请求带上这个令牌，服务端就能知道"你是谁"，不需要反复输密码。

**类比**：你去游乐园买票，检票后给你盖个章。之后你进出各个项目，工作人员看你的章就知道你买过票了，不用你每次都掏钱包。这个章就是 JWT。

### 怎么做的？

- **登录时**：用户输入用户名+密码，后端验证正确后生成一个 JWT token 返回。token 里包含了用户ID、用户名、角色，用密钥签名防篡改。
- **请求时**：前端在 HTTP 请求头里带上 `Authorization: Bearer <token>`。
- **验证时**：后端写了一个全局拦截器 `UserAuthInterceptor`，拦截所有 `/api/**` 请求，解析 token 并把 userId 放到请求上下文里。
- **权限控制**：自定义 `@RequireAuth` 注解，标在需要登录的接口上。公开接口（如技能广场、悬赏列表）不需要注解也能访问。

### 代码在哪？

| 组件 | 位置 |
|------|------|
| JWT 工具类 | `skill-common/.../JwtUtil.java` — 生成token、解析token、校验签名 |
| 拦截器 | `skill-gateway/config/UserAuthInterceptor.java` — 拦截所有请求，解析token |
| 注解 | `skill-common/.../RequireAuth.java` — 标记需要登录的接口 |
| 拦截器注册 | `skill-gateway/config/WebMvcConfig.java` — 把拦截器注册到Spring |

### 答辩怎么说？

> "我们实现了基于 JWT 的无状态认证。用户登录后获得 token，之后所有请求通过全局拦截器自动解析身份。我们自定义了 @RequireAuth 注解来做声明式权限控制——需要登录的方法加个注解就行，不需要写重复的判断代码。"

## 2. 设计模式（3种）

### 2.1 状态模式 —— 订单状态机

**是什么**：订单的状态流转非常复杂（待确认→进行中→待确认完成→已完成/已取消），每种状态下能做的操作不同。状态模式把每种状态的处理逻辑封装起来，避免写一大堆 if-else。

**类比**：电梯门——关门状态按"开"才有反应，开门状态按"关"才有反应。状态决定了哪些操作是合法的。

**代码在哪**：`skill-order-service/.../OrderServiceImpl.java`

订单状态流转代码（5个状态 + 状态间合法转换）：
- `createOrder` → 状态=待确认(1)
- `confirmOrder` → 卖方确认 → 待确认(1)→进行中(2)，同时冻结买方时间币
- `buyerConfirmComplete` + `sellerConfirmComplete` → 双方确认 → 进行中(2)→待确认完成(3)→已完成(4)，解冻并转账
- `cancelOrder` → 待确认(1)→已取消(5)

### 2.2 拦截器模式 —— JWT 认证

**是什么**：拦截器是 Spring 框架提供的一种机制，可以在请求到达 Controller 之前统一处理。我们把 JWT 验证逻辑放在拦截器里，让所有 API 自动完成身份解析，Controller 代码不需要重复写验证逻辑。

**类比**：写字楼的前台——所有人进门时统一登记，之后去哪个办公室就不需要再登记了。

**代码在哪**：`skill-gateway/config/UserAuthInterceptor.java`

### 2.3 模板方法模式 —— BaseEntity

**是什么**：每张表都有 `id`、`create_time`、`update_time` 三个字段。如果每个实体类都写一遍，又重复又容易忘。我们用 `BaseEntity` 作为父类，定义好这三个公共字段，其他实体继承它就行。

**类比**：Word 模板——每次写报告不用从头排版，直接基于模板改内容。

**代码在哪**：`skill-common/.../BaseEntity.java`（定义 id/createTime/updateTime），所有实体类 `extends BaseEntity`。

### 答辩怎么说？

> "我们用了三种设计模式。状态模式管理订单的5种状态流转，拦截器模式统一处理JWT认证，模板方法模式通过BaseEntity避免每个实体重复定义公共字段。三种模式都写入了详细设计文档第6章。"

## 3. Swagger 接口文档

### 是什么？

Swagger（SpringDoc OpenAPI）是一个自动生成 API 文档的工具。你在 Controller 上写好注解，它就能自动生成一个网页，列出所有接口、参数、返回值，还能在线测试。

**类比**：淘宝商品详情页——你不需要问卖家"这个东西有什么功能"，点进去自己看就行。

### 怎么做的？

- 引入 `springdoc-openapi-starter-webmvc-ui` 依赖（版本 2.3）
- 无需额外配置，Spring Boot 3.2 自动识别
- 访问 `http://localhost:8080/swagger-ui.html` 即可看到所有 API

### 代码在哪？

`skill-gateway/pom.xml` 中的依赖：
```xml
<dependency>
    <groupId>org.springdoc</groupId>
    <artifactId>springdoc-openapi-starter-webmvc-ui</artifactId>
    <version>2.3.0</version>
</dependency>
```

### 答辩怎么说？

> "我们集成了 SpringDoc OpenAPI 2.3，启动后端后访问 swagger-ui.html 就能看到所有API接口文档，支持在线测试，前后端联调非常方便。"

## 4. 单元测试（59个）

### 是什么？

单元测试是对代码最小单元（方法）的自动化测试——写代码来测试代码。我们用 JUnit 5 写测试，用 Mockito 模拟数据库操作，不连真实数据库就能验证业务逻辑。

**类比**：造房子时的混凝土试块检测——不等到房子塌了才知道有问题，提前抽样测试。

### 怎么做的？

- 测试框架：JUnit 5 + Mockito（MockitoExtension）
- 用 `@Mock` 模拟 Mapper（不连真实数据库），`@InjectMocks` 注入被测试的 Service
- 覆盖三种场景：正常流程、异常边界（金额≤0、空参数等）、权限校验（不是本人不能操作）

### 覆盖了哪些？

| 测试类 | 数量 | 覆盖内容 |
|--------|:--:|------|
| `OrderServiceImplTest` | 30个 | 创建订单(5)、确认接单(5)、买方确认(5)、卖方确认(5)、完成订单(5)、取消订单(5) |
| `UserServiceImplTest` | 29个 | 注册(4)、登录(3)、个人信息(3)、更新资料(3)、关注/取关(6)、关注列表(2)、是否关注(2)、头像更新(2)、用户搜索(2)、用户状态(2) |

### 代码在哪？

- `skill-order-service/src/test/java/.../OrderServiceImplTest.java`
- `skill-user-service/src/test/java/.../UserServiceImplTest.java`

### 答辩怎么说？

> "我们为两个核心 Service 写了59个单元测试，用 Mockito 模拟数据库层，不依赖真实数据库。每个方法覆盖正常+异常+边界三种情况。运行 mvn test 就能全部跑一遍，保证改动不会引入新bug。"

## 5. Docker 部署

### 是什么？

Docker 把应用和它需要的环境（MySQL、Java、Node等）一起打包成"容器"，在任意机器上一条命令就能跑起来，不用手动装环境。

**类比**：搬家公司的打包箱——你不需要操心每样东西怎么搬，箱子到你新家直接拆开就用。

### 怎么做的？

`docker-compose.yml` 编排了4个容器：

| 容器 | 内容 | 端口 |
|------|------|:--:|
| MySQL | 数据库（自动执行 init.sql 建表） | 3307 |
| Backend | Spring Boot JAR（JRE 17 Alpine） | 8080 |
| Frontend-User | 用户端（Nginx 托管静态文件） | 5173 |
| Frontend-Admin | 管理后台（Nginx 托管静态文件） | 5174 |

### 代码在哪？

`项目代码/docker-compose.yml` — 完整的4容器编排配置

### 关键命令

```bash
docker compose up -d          # 一键启动全部4个容器
docker compose up -d --build backend  # 仅重建后端
docker compose down           # 停止全部
docker compose down -v        # 停止+清除数据库（重置）
```

### 答辩怎么说？

> "我们完成了 Docker 容器化部署，用 docker-compose 编排了4个容器——MySQL、后端Spring Boot、用户前端和管理后台。一条 docker compose up -d 命令就能在任意装了Docker的机器上跑起来，符合课程要求的容器化部署标准。"
